# versioned-object-store-go

一套本机可复现的版本化对象存储服务：以本地磁盘存放对象数据、以本地 JSON 元数据文件记录版本与分片上传状态，模拟对象、多版本与分片上传语义。不依赖任何外部服务、真实凭据或联网资源。

## 构建与验证

```sh
go build ./...        # 编译
go vet ./...          # 静态检查
go test ./...         # 全部测试
go test -race ./...   # 竞态检测（并发写入 / GC 交错场景）
go test -v ./...      # 查看运行日志：对象键、版本号、分片号与判定依据
```

## 磁盘布局

```
<Dir>/
  LOCK                       目录独占锁文件（flock，内容为持有方 pid）
  meta.json                  元数据（写 .tmp + fsync + rename 原子提交）
  data/<sha1(key)>/<verID>   对象版本数据（先写 .tmp-<verID> 再 rename 就位）
  uploads/<uploadID>/part-N  进行中的分片（先写 .tmp 再 rename 就位）
```

**提交顺序保证**：数据文件先完整落盘（fsync + rename），元数据后原子提交。
崩溃只可能留下"有数据、无元数据"的孤儿文件（恢复/GC 可回收），
绝不留下"元数据引用了缺失数据"的悬挂引用或半写版本。

## 目录独占

- `Open` 成功即持有 `<Dir>/LOCK` 上的独占文件锁（`flock(LOCK_EX|LOCK_NB)`），
  同一数据目录同一时刻只能被一个使用者打开——同一进程内重复打开与
  多个进程分别打开都会被拒绝。
- 被拒绝方收到 `*DirLockedError`（可用 `errors.Is(err, ErrDirLocked)` 判定），
  其中 `HolderPID` 记录持有方进程号便于诊断；被拒绝方在取锁前不会触碰
  目录内任何数据（包括恢复清理），因此不会改动已有数据。
- 持有者 `Close` 或进程退出（含被强杀）后，锁由内核自动释放，后来者即可正常打开。
- 同一持有者可被多 goroutine 并发使用：对同一键的并发写由互斥锁串行化，
  各自获得独立版本号，不会互相覆盖或丢失先写的数据。

## 崩溃后的判定规则

`Open` 时区分两类情形：

1. **可安全丢弃的崩溃残留（自动修复）**：未提交的 `meta.json.tmp`、
   无元数据引用的数据文件与临时文件、已终结/未知上传会话目录、
   initiated 会话中未登记的分片文件。这些只可能源于"数据先落盘、
   元数据后提交"的写入顺序，丢弃不影响任何可见版本，修复后照常启动。
2. **真正的数据损坏（打开失败）**：元数据文件本身被截断/破坏
   （`CorruptionError.Meta` 非空）；或某个仍被元数据引用的版本，
   其数据文件缺失、尺寸不符或 SHA-256 校验和不匹配
   （`CorruptionError.Versions` 逐个指出键、版本号与原因）。
   此类情形 `Open` 返回 `*CorruptionError`（可用
   `errors.Is(err, ErrCorruption)` 判定），**不会**静默抹除有问题的版本、
   不会让读取回退到更旧版本，也不会改动现场——修复数据后重新打开即可，
   同样的场景反复重启结论保持一致。

**兼容范围**：旧版本存储的元数据可能缺少 `sha256` 字段，打开时对这些版本
只做"存在性 + 尺寸"校验；新写入的版本（含分片上传完成的版本）一律记录
SHA-256 并做内容校验。磁盘布局与元数据格式向后兼容，旧目录可直接打开。

## 历史版本保留回收

- `RetainVersions(key, keep)` / `RetainAll(keep)`：对指定键（或整个存储的
  每个键）只保留最近 `keep` 个版本（按创建顺序，含当前版本与删除标记），
  超出窗口的旧版本其元数据条目与数据文件一并回收。`keep < 1` 按 1 处理，
  当前版本始终保留。
- 删除标记语义不受影响：当前版本为删除标记时 `Get` 仍返回 `ErrDeleted`，
  窗口内的历史版本与删除标记仍可寻址。
- 与并发读写交错自洽：正在被读取的版本数据不会被删除——对应版本本次
  暂缓回收并记入报告的 `Deferred`，读取关闭后再次回收才会真正删除；
  回收与写入互斥串行，当前版本与窗口内版本不受任何影响。
- 返回 `RetentionReport`：`Removed`（已回收的键/版本/字节数）、
  `Deferred`（暂缓的版本）、`ReclaimedBytes`（实际删除文件的字节数，
  与回收前后数据目录磁盘占用差一致）。

## 版本与条件写入语义

- 每次 `Put` 产生一个全局单调递增的版本号（`v00000001`…），同一键的并发写入
  由互斥锁串行化，各自获得独立版本号，互不覆盖、不留半写数据。
- `Get(key)` 返回当前版本；`GetVersion(key, versionID)` 按版本号寻址，
  被覆盖、被删除的历史版本内容不变、始终可读。
- `Delete(key)` 写入删除标记（tombstone）作为新的当前版本：`Get` 返回
  `ErrDeleted`，历史版本仍可寻址读取，重复删除返回 `ErrNotFound`。
- 条件写入前置条件（`PutOptions`）：
  - `IfAbsent`：要求键当前不存在（或当前版本为删除标记）；
    冲突返回 `*PreconditionError{Kind: PreconditionKeyExists}`。
  - `ExpectVersion`：要求键的当前版本号与之相等；
    冲突返回 `*PreconditionError{Kind: PreconditionVersionMismatch}`，
    并携带 `Expected`/`Actual` 便于排查。
  - 两类失败均可用 `errors.Is(err, ErrPreconditionFailed)` 判定、
    `errors.As` 取出 `*PreconditionError` 区分原因；被拒绝的写入不产生任何版本。

## 分片上传状态机

```
            CreateUpload
                 │
                 ▼
            ┌──────────┐  UploadPart(乱序/重复均可，重复为幂等覆盖)
            │ initiated │◄─────────────────────────────┐
            └──────────┘                               │
             │          │                              │
   Complete  │          │ Abort                        │ UploadPart
             ▼          ▼                              │
       ┌──────────┐  ┌────────┐                        │
       │ completed │  │ aborted │───────────────────────┘(拒绝)
       └──────────┘  └────────┘
```

- 分片编号合法范围为 `[1, MaxParts]`，越界返回 `ErrPartNumberInvalid`。
- `CompleteUpload(parts)` 按给定编号顺序拼接为新版本：
  - 引用未上传分片 → `ErrPartMissing`（指明缺失编号）；
  - 重复完成 → 幂等返回首次完成的版本号，不产生新版本；
  - 已中止 → `ErrUploadAborted`。
- `AbortUpload`：重复中止幂等成功；已完成 → `ErrUploadCompleted`。
- 终态（completed/aborted）会话上的 `UploadPart` 分别返回
  `ErrUploadCompleted` / `ErrUploadAborted`。
- 失败或中止的上传不产生任何可见对象；其分片目录在状态转换时删除，
  崩溃残留由重启恢复或 `GC` 清除，不会留下无法回收的分片。

## 崩溃恢复与空间回收

- `Open` 时执行恢复：丢弃未提交的 `meta.json.tmp`；删除无元数据引用的
  数据文件；清除已终结/未知上传会话的目录及 initiated 会话中未登记的分片文件。
  元数据引用的版本数据缺失/不一致时打开失败（见上文"崩溃后的判定规则"）。
- `GC` 只删除无任何元数据引用的文件，因此不影响任何可见对象与版本；
  正在被读取的版本其数据文件始终被引用，回收期间读取可正常完成。
  返回 `GCReport`（删除的数据文件数、上传目录数、回收字节数）。
- 历史版本的窗口化回收见上文"历史版本保留回收"（`RetainVersions`/`RetainAll`）。

## 可配置项（Config）

| 字段       | 说明                                       | 默认值          |
|------------|--------------------------------------------|-----------------|
| `Dir`      | 本地数据根目录                             | 必填            |
| `MaxParts` | 单次分片上传允许的最大分片数               | 10000           |
| `Logger`   | 运行日志（`log/slog`）                     | `slog.Default()`|

## 测试覆盖

`go test -v ./...` 可按用例名查看每类场景的判定日志与通过情况：

- `store_test.go`：版本寻址、条件写入冲突原因区分、并发无条件写入
  （版本互不覆盖）、并发 `IfAbsent`（仅一个成功）、删除后历史可读。
- `multipart_test.go`：乱序/重复分片、越界分片、缺失分片、重复完成幂等、
  重复中止幂等、终态拒绝、中止后无可见对象与残留分片。
- `recovery_test.go`：重启后已提交状态保持、崩溃残留清理、
  缺失版本数据时打开失败且结论可复现、GC 与读写并发交错下的状态自洽。
- `lock_test.go`：同进程/跨进程目录独占（拒绝原因可区分、被拒方不改数据、
  关闭后可交接）、同一持有者并发写同一键不丢数据。
- `corruption_test.go`：元数据截断、数据篡改（校验和不匹配）、尺寸不符
  均打开失败并指出键与版本；修复后可打开；安全残留自动修复且结论一致。
- `retention_test.go`：按窗口回收与磁盘占用对账、删除标记语义保持、
  全库回收、在读版本暂缓回收、回收与并发读写交错自洽、边界参数。
