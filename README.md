# versioned-object-store-go

一套本机可复现的版本化对象存储服务：以本地磁盘存放对象数据、以本地 JSON 元数据文件记录版本与分片上传状态，模拟对象、多版本与分片上传语义。不依赖任何外部服务、真实凭据或联网资源。

## 构建与验证

```sh
go build ./...        # 编译
go vet ./...          # 静态检查
go test ./...         # 全部测试
go test -race ./...   # 竞态检测（并发写入 / GC 交错场景）
go test -v ./...      # 查看运行日志：对象键、版本号、分片号与判定依据
```

## 磁盘布局

```
<Dir>/
  LOCK                       目录独占锁文件（flock + 持有者诊断信息）
  meta.json                  元数据（写 .tmp + fsync + rename 原子提交）
  data/<sha1(key)>/<verID>   对象版本数据（先写 .tmp-<verID> 再 rename 就位）
  uploads/<uploadID>/part-N  进行中的分片（先写 .tmp 再 rename 就位）
```

**提交顺序保证**：数据文件先完整落盘（fsync + rename），元数据后原子提交。
崩溃只可能留下"有数据、无元数据"的孤儿文件（恢复/GC 可回收），
绝不留下"元数据引用了缺失数据"的悬挂引用或半写版本。

## 目录独占（多实例误用防护）

- `Open` 时对 `<Dir>/LOCK` 加排他 `flock`（非阻塞）：同一数据目录同一时刻
  只允许一个使用者打开，同一进程重复打开与多个进程同时打开都会被拒绝。
- 被拒绝时返回 `*LockError`（可用 `errors.Is(err, ErrDirLocked)` 判定），
  其中 `Holder` 字段携带持有者的 `pid/host/since` 诊断信息；被拒绝方拿不到
  `Store` 句柄，无法改动已有数据。
- 持有者 `Close` 或进程退出（内核自动释放 flock）后，后来者才能正常打开。
- `LOCK` 文件在 `Close` 后保留（仅作诊断参考），锁状态以 flock 为准。
- 独占打开期间，多个写者并发写同一个键由互斥锁串行化：每次写入产生独立
  版本，互不覆盖、不丢失。
- 兼容范围：依赖 Unix `flock`，面向 Linux/Unix 本机部署。

## 版本与条件写入语义

- 每次 `Put` 产生一个全局单调递增的版本号（`v00000001`…），同一键的并发写入
  由互斥锁串行化，各自获得独立版本号，互不覆盖、不留半写数据。
- `Get(key)` 返回当前版本；`GetVersion(key, versionID)` 按版本号寻址，
  被覆盖、被删除的历史版本内容不变、始终可读。
- `Delete(key)` 写入删除标记（tombstone）作为新的当前版本：`Get` 返回
  `ErrDeleted`，历史版本仍可寻址读取，重复删除返回 `ErrNotFound`。
- 条件写入前置条件（`PutOptions`）：
  - `IfAbsent`：要求键当前不存在（或当前版本为删除标记）；
    冲突返回 `*PreconditionError{Kind: PreconditionKeyExists}`。
  - `ExpectVersion`：要求键的当前版本号与之相等；
    冲突返回 `*PreconditionError{Kind: PreconditionVersionMismatch}`，
    并携带 `Expected`/`Actual` 便于排查。
  - 两类失败均可用 `errors.Is(err, ErrPreconditionFailed)` 判定、
    `errors.As` 取出 `*PreconditionError` 区分原因；被拒绝的写入不产生任何版本。

## 分片上传状态机

```
            CreateUpload
                 │
                 ▼
            ┌──────────┐  UploadPart(乱序/重复均可，重复为幂等覆盖)
            │ initiated │◄─────────────────────────────┐
            └──────────┘                               │
             │          │                              │
   Complete  │          │ Abort                        │ UploadPart
             ▼          ▼                              │
       ┌──────────┐  ┌────────┐                        │
       │ completed │  │ aborted │───────────────────────┘(拒绝)
       └──────────┘  └────────┘
```

- 分片编号合法范围为 `[1, MaxParts]`，越界返回 `ErrPartNumberInvalid`。
- `CompleteUpload(parts)` 按给定编号顺序拼接为新版本：
  - 引用未上传分片 → `ErrPartMissing`（指明缺失编号）；
  - 重复完成 → 幂等返回首次完成的版本号，不产生新版本；
  - 已中止 → `ErrUploadAborted`。
- `AbortUpload`：重复中止幂等成功；已完成 → `ErrUploadCompleted`。
- 终态（completed/aborted）会话上的 `UploadPart` 分别返回
  `ErrUploadCompleted` / `ErrUploadAborted`。
- 失败或中止的上传不产生任何可见对象；其分片目录在状态转换时删除，
  崩溃残留由重启恢复或 `GC` 清除，不会留下无法回收的分片。

## 崩溃恢复、损坏判定与空间回收

`Open` 时把磁盘状态分成两类处理：

- **可安全丢弃的崩溃残留**（自动修复后继续启动）：
  未提交的 `meta.json.tmp`、无元数据引用的数据文件与临时文件、
  已终结/未知上传会话的目录、initiated 会话中未登记的分片文件。
- **真正的数据损坏**（打开失败，返回 `*CorruptionError`，
  可用 `errors.Is(err, ErrCorruption)` 判定）：
  - 元数据仍引用的版本其数据文件缺失、大小与记录不一致、
    或内容与记录的 SHA256 校验和不一致；
  - `meta.json` 本身无法解析（被截断/写坏）。
  此时 `Open` 不改动任何磁盘状态（不清理、不持久化），
  反复打开结论一致；错误中逐一列出出问题的键与版本号及原因，
  绝不静默抹掉有问题的版本、让读取静默回退到更旧版本。
  人工修复（如补回正确的数据文件）后同一目录可正常打开。

每个版本提交时记录内容 SHA256 校验和（`meta.json` 中的 `sha256` 字段），
打开校验时逐版本核对；旧格式数据无校验和字段时仅校验存在性与大小（向后兼容）。

- `GC` 只删除无任何元数据引用的文件，因此不影响任何可见对象与版本；
  正在被读取的版本其数据文件始终被引用，回收期间读取可正常完成。
  返回 `GCReport`（删除的数据文件数、上传目录数、回收字节数）。

## 历史版本保留回收

- `RetainVersions(key, keep)` / `RetainAll(keep)`：对单个键或整个存储
  只保留最近 `keep` 个版本（`keep >= 1`），超出窗口的旧版本条目连同其
  数据文件一并回收。
- 当前版本（无论是否为删除标记）始终在窗口内，删除标记语义与窗口内
  历史版本完全不受影响；被回收的版本按版本号寻址时返回 `ErrNotFound`。
- 与并发读写交错是安全的：已开始的读取持有文件描述符，其数据文件被
  回收后读取仍可完成；新的读写由互斥锁串行化，只能看到保留窗口内的版本。
- 返回 `RetentionReport`：逐键列出被回收的版本号与字节数，
  `ReclaimedBytes` 按实际删除的数据文件大小统计，可与磁盘占用变化核对。

## 可配置项（Config）

| 字段       | 说明                                       | 默认值          |
|------------|--------------------------------------------|-----------------|
| `Dir`      | 本地数据根目录                             | 必填            |
| `MaxParts` | 单次分片上传允许的最大分片数               | 10000           |
| `Logger`   | 运行日志（`log/slog`）                     | `slog.Default()`|

## 测试覆盖

`go test -v ./...` 运行时每个新增用例会打印 `scenario: <类别> / <场景>` 标识，
配合运行日志可看出覆盖了哪几类场景及每类的通过情况：

- `store_test.go`：版本寻址、条件写入冲突原因区分、并发无条件写入
  （版本互不覆盖）、并发 `IfAbsent`（仅一个成功）、删除后历史可读。
- `multipart_test.go`：乱序/重复分片、越界分片、缺失分片、重复完成幂等、
  重复中止幂等、终态拒绝、中止后无可见对象与残留分片。
- `recovery_test.go`：重启后已提交状态保持、崩溃残留清理、
  引用缺失数据的版本导致打开失败（损坏判定）、GC 与读写并发交错的状态自洽。
- `lock_test.go`（目录独占）：同进程重复打开拒绝并携带持有者信息、
  Close 后放行、跨进程占用拒绝（持有者退出后放行）、
  独占期间并发写同键不丢失、LOCK 文件诊断留存。
- `corruption_test.go`（崩溃判定）：数据被篡改（校验和不一致）、
  数据被截断（大小不一致）、meta.json 写坏均打开失败且可区分；
  人工修复后可打开；安全残留自动修复且反复重启结论一致。
- `retention_test.go`（保留回收）：单键/全库保留窗口、删除标记语义保持、
  回收报告字节数与磁盘实际占用核对、与并发读写交错自洽、参数校验与空转。
